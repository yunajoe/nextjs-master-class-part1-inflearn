# Composition Pattern

## 1. 두 세계의 만남과 렌더링 원리

- **서버 컴포넌트:** DB 통신, 무거운 연산, 보안 키 사용 등 서버 환경에서 렌더링을 끝내고 완성된 HTML 뼈대(RSC Payload)를 만듭니다.
- **`use client`의 진짜 의미:** 무조건 아래로 전파되는 '감염병'이 아니라, "여기서부터 브라우저 영역입니다"라는 경계선(Boundary)을 정의하는 선언입니다.
- **참조 마커(Reference Marker):** 서버가 렌더링 중 `use client` 컴포넌트를 만나면 파고들지 않고, 브라우저가 채워 넣을 빈 구멍으로 표시한 뒤 서버 렌더링을 마칩니다.

## 2. 나뭇잎 컴포넌트 (Leaf Component) 패턴

- **전략:** 굵은 줄기(페이지 전체, 레이아웃)는 무겁고 튼튼한 서버 컴포넌트로 두고, 바람에 흔들리는 작은 잎사귀(좋아요 버튼, 모달 등 상호작용 요소)만 `use client`로 아주 작게 떼어냅니다.
- **효과:** 브라우저로 전송되는 JavaScript 번들 크기를 최소화하여 초기 로딩 속도를 극대화합니다.

## 3. 하이드레이션 (Hydration) 과정

1. **서버의 HTML 배달:** 서버가 텍스트와 클라이언트 컴포넌트의 껍데기(UI)를 먼저 만들어 브라우저로 던져 즉시 화면에 노출합니다.
2. **JS 번들 다운로드:** 브라우저가 필요한 클라이언트 JS 파일을 백그라운드에서 다운로드합니다.
3. **하이드레이션:** 정적인 HTML 뼈대에 JS를 밀착시켜 `onClick` 같은 이벤트 리스너를 붙여 생명력을 불어넣습니다.

## 4. 조립의 역방향 함정과 합성(Composition) 패턴

- **❌ 절대 금지 (역방향 임포트):** 클라이언트 컴포넌트 내부에서 서버 컴포넌트를 직접 `import`하면, 서버 컴포넌트가 강제로 클라이언트로 전환되어 번들에 포함되고 보안/성능 치명상을 입습니다.
- **⭕ 올바른 해결책 (Children 합성 패턴):**
- 클라이언트 컴포넌트는 액자(`children` 구멍) 역할만 담당합니다.
- 서버(부모)가 이미 완벽하게 렌더링해 둔 서버 컴포넌트를 `children`이나 `props` 형태로 끼워 넣어 전달합니다.
- 결과적으로 클라이언트 컴포넌트 안에 위치하더라도 서버 컴포넌트의 본질(서버 전용 실행 및 번들 미포함)이 완벽하게 유지됩니다.

## 5. `'use client'` 경계와 컴포넌트 생존 원리 요약

- **`'use client'`의 본질:** 아래로 무조건 전파되는 감염병이 아니라, "여기서부터 브라우저 영역입니다"라는 경계선(Boundary)을 정의하는 선언입니다.
- **하위 컴포넌트의 성질을 결정하는 기준 (`import` vs `children`):**
- **직접 `import`하는 경우:** 클라이언트 컴포넌트 안에서 하위 컴포넌트를 직접 불러오면, 그 하위 컴포넌트 역시 강제로 클라이언트 컴포넌트로 전환되어 브라우저로 JS 번들이 전송됩니다.
- **`children`이나 `props`로 주입받는 경우:** 서버(부모)가 이미 완벽하게 렌더링을 끝마친 결과물(페이로드)을 건네받는 방식입니다. 클라이언트는 코드 내용도 모른 채 단순히 UI 트리 위에 자리를 배치하는 것뿐이므로, 서버 컴포넌트의 본질이 온전히 유지됩니다.
