### 01. React(Library) vs Next.js(Framework): 아키텍처와 철학

```
Next.js는 **'설정(Configuration)'**의 늪에서 벗어나 **'관습(Convention)'**을 따름으로써, 개발자가 인프라 고민 없이 비즈니스 로직(화면/기능)에만 집중할 수 있게 해줍니다.

```

1. Library의 한계: React만의 '빈 땅'과 설정 지옥

- 비유: 셀프 건축 (UI라는 벽돌만 제공되므로 라우터, 상태관리, 번들러 등을 개발자가 직접 구해서 집을 지어야 함)
- 주요 Pain Points:

```
- 높은 피로도: 필요한 외부 라이브러리를 일일이 찾고, 설치하고, 각각의 규칙을 학습해야 함.
- 유지보수 부담: 페이지가 추가될 때마다 라우팅 설정 파일(BrowserRouter, Routes 등)을 수동으로 업데이트해야 함.
- 제어의 주도권: 전체 애플리케이션의 구조와 흐름을 개발자가 직접 통제하고 책임져야 함.

```

2. Framework의 등장: 제어의 역전(IoC) 패러다임

- 비유: 풀옵션 모델하우스 / 호텔 시스템 (골조와 배관이 이미 완성되어 있으며, 특정 규칙에 맞춰 방을 채우기만 하면 됨)
- 핵심 개념: 제어의 역전 (Inversion of Control, IoC)

```
과거 (React): 개발자의 코드가 주도권을 잡고 외부 도구를 호출하는 방식.
현재 (Next.js): 프레임워크가 뼈대와 흐름을 통제하며, 개발자의 코드는 부품처럼 호출당하는 방식.

```

3. App Router 방식 (Next.js 15 표준)라우팅 설정을 코드 작성으로 하지 않고, 폴더 구조와 파일명(관습)으로 자동 해결합니다.

```
* `app/page.tsx` → `/` (메인 화면)
* `app/about/page.tsx` → `/about` (About 화면)

> 개발자는 완성된 컴포넌트를 `export default`로 넘겨주기만 하면, 프레임워크가 알아서 최적화 및 렌더링을 제어합니다.

```

4. 비교 요약: Configuration vs Convention

| 구분          | React (Library)          | Next.js (Framework)                         |
| :------------ | :----------------------- | :------------------------------------------ |
| **핵심 철학** | 설정 (Configuration)     | 관습 (Convention)                           |
| **주도권**    | 개발자에게 있음          | 프레임워크에게 있음 (IoC)                   |
| **장점**      | 높은 자유도              | 높은 생산성, 비즈니스 로직에 100% 집중 가능 |
| **단점**      | 설정 및 관리 피로도 증가 | 프레임워크 규칙에 종속됨                    |

### 02. Next.js 파일 시스템 라우팅 (File-system Routing)

```
Next.js에서는 **"폴더 생성이 곧 주소 생성"**입니다. 복잡한 수동 매핑 작업 없이, 폴더 구조가 곧 웹 사이트의 지도가 됩니다.
```

1. 수동 지도의 늪 (도입 전: React Router)
   과거에는 페이지 컴포넌트를 만든 후, 주소와 일일이 짝지어 주는 수동 배선 작업이 필수였습니다.

```
🔍 주요 문제점
- 등록 누락: 페이지를 만들어도 라우터 설정 파일(Routes)에 등록하지 않으면 404 에러 발생

- 휴먼 에러: URL 경로 입력 시 오타(path="/abput") 가능성

- 유지보수 저하: 페이지 수가 늘어날수록 라우팅 설정 코드 길이가 기하급수적으로 증가

```

2. 파일 시스템 라우팅 (도입 후: Next.js)

- app 디렉토리 하위의 폴더 위치와 파일명(page.tsx)이 자동으로 인터넷 주소(URL)로 변환됩니다.

```

app/
├── page.tsx          👉 mysite.com/ (메인)
├── about/
│   └── page.tsx      👉 mysite.com/about
└── login/
    └── page.tsx      👉 mysite.com/login

```

- 핵심 이점

```
- 설정 파일 불필요: 별도의 라우팅 수첩/설정 코드 완전 삭제

- 높은 직관성: 폴더 구조만 보고도 사이트 전체 메뉴 파악 가능

- 자동화: app/폴더/page.tsx 생성 즉시 외부 접근 가능한 주소 할당
```

3. 만능 열쇠 [id] (동적 라우팅, Dynamic Routes)

- 수만, 수억 개의 상품 페이지가 필요할 때 대괄호 [] 폴더를 사용하여 가변적인 경로를 처리합니다.

```
app/
└── products/
    └── [id]/         👈 변수형 만능 폴더
        └── page.tsx

```

```
- 사용자 요청: [mysite.com/products/galaxy](https://mysite.com/products/galaxy) 접속

- Next.js 매핑: products/ 하위에 일치하는 고정 폴더가 없으므로 [id] 폴더로 안내

- 파라미터 전달: 입력값 galaxy를 params 객체에 담아 page.tsx 컴포넌트로 전달

- 화면 렌더링: 컴포넌트가 params.id("galaxy")를 확인하여 해당하는 데이터 출력

```

| 구분                   | 과거 (React Router)                                                     | 현재 (Next.js)                                                       |
| :--------------------- | :---------------------------------------------------------------------- | :------------------------------------------------------------------- |
| **비유**               | 호텔 프런트                                                             | 아파트 동/호수                                                       |
| **특징**               | 직원이 장부를 확인하고 안내해야만 방을 찾음<br>(설정 누락 시 길을 잃음) | 별도 안내자 없이 주소(`app/about/page.tsx`)만으로 정확히 찾아감      |
| **`[id]` 동적 라우팅** | -                                                                       | 빈 명찰<br>('철수'가 오면 철수 명찰, '영희'가 오면 영희 명찰로 변신) |

### 03.렌더링 패러다임의 진화: CSR -> SSR -> RSC

```
Next.js App Router의 **RSC(React Server Components)**는 무거운 로직과 라이브러리를 오직 서버에서만 실행하여, 브라우저로 전송되는 JS 용량을 비약적으로 줄여주는 혁신적인 아키텍처입니다.
```

1. 1세대: CSR (Client Side Rendering)

- 개념: 브라우저(Client)가 화면을 그리는 모든 연산을 담당하는 방식.
- 비유: 조립되지 않은 이케아 가구 박스
- 공장(서버)은 빈 상자(HTML)와 두꺼운 설명서(JS)만 전달. 브라우저는 설명서를 다 읽은 후 다시 나사(데이터)를 요청해 화면을 직접 조립함.

```
주요 Pain Point: 워터폴(Waterfall) 지연
 1. 빈 HTML 다운로드 -> 2. 거대한 JS 로드 및 실행 -> 3. useEffect 내 fetch로 API 데이터 요청 -> 4. 데이터 수신 후 화면 표시결과: 사용자는 하얀 화면과 로딩 스피너를 오래 마주함 + 구글 검색 봇이 빈 페이지로 인식(SEO 불리).

2. 2세대: SSR (Server Side Rendering)
- 개념: 서버에서 HTML을 미리 완성하여 브라우저로 전달하는 방식.
- 비유: 랩으로 꽁꽁 싸인 완성형 가구
- 서버가 이미 조립된 가구를 보내주어 즉시 눈으로 볼 수 있지만, 랩(JS)을 벗겨내기 전까지는 스위치나 서랍을 조작할 수 없음.
```

```
- 한계: 초기에 화면은 빨리 보이지만, 버튼 클릭 등 상호작용이 가능해지는 하이드레이션(Hydration) 단계까지 대용량 JS 파일을 여전히 다운로드해야 함.

```

3. 3세대: RSC (React Server Components)

- 개념: "서버에서 실행될 코드는 아예 브라우저로 보내지 않는다"는 최신 패러다임 (Next.js 15 App Router의 기본값).
- 비유: 최고급 장비로 시공 완료된 붙박이 가구 (전문가가 이미 완벽하게 설치를 끝냈으므로, 사용자는 망치나 설명서 없이 즉시 사용하기만 하면 됨)

```javascript
// 1. 'use client'가 없으므로 서버에서만 실행되는 서버 컴포넌트
import db from "@/lib/db";

export default async function ProductPage() {
  // 2. DB 직접 조회 (네트워크 통신 지연 없음, 보안 우수)
  const data = await db.product.findMany();

  // 3. 브라우저에는 렌더링 결과(HTML/RSC Payload)만 전송 (Zero JS Bundle)
  return (
    <div>
      {data.map((item) => (
        <div key={item.id}>{item.name}</div>
      ))}
    </div>
  );
}
```

```
- 핵심 이점 (Zero Bundle Size)
보안성: 데이터베이스 직접 접근 코드가 클라이언트에 절대로 노출되지 않음.
성능: 무거운 로직과 npm 라이브러리가 브라우저 JS 번들 크기에 영향을 주지 않음.

1. npm install을 하는 시점 (개발 / 빌드 단계)
- npm install은 CSR이든, SSR이든, 서버 컴포넌트든 관계없이 항상 개발자의 컴퓨터나 배포 서버(Vercel, AWS 등)에서만 실행됩니다.

- 사용자의 브라우저(크롬 등)에서는 절대 npm install이 실행되지 않습니다.

2. 사용자가 사이트에 접속할 때 (네트워크 전송 단계)
- 진짜 차이는 "개발자/서버가 npm install로 받아둔 그 라이브러리 파일(JS)을 사용자의 브라우저로 보내주느냐, 안 보내주느냐"에서 발생합니다.
- 기존 React (CSR) 및 클라이언트 컴포넌트:
서버에 있는 npm 라이브러리 코드를 웹팩(Bundler)이 잘게 뭉쳐서(Bundle) 사용자 브라우저로 다 보냅니다.
사용자는 사이트에 들어올 때마다 그 무거운 라이브러리 JS 파일들을 인터넷으로 일일이 다운로드해야 합니다.
- Next.js 서버 컴포넌트 (RSC):
npm 라이브러리 코드가 오직 서버 내부에서만 돌아가고, 브라우저로는 '연산 결과(글자/HTML)'만 전달됩니다.
따라서 사용자의 브라우저는 라이브러리 코드를 다운로드할 필요가 전혀 없습니다. (0바이트)

[개발자/배포 서버] ── (npm install로 라이브러리 보유)
       │
       ├─► ① CSR / 클라이언트 컴포넌트:
       │    라이브러리 JS 코드를 파일로 묶어서 인터넷으로 브라우저에 '전송' (다운로드시킴)
       │
       └─► ② 서버 컴포넌트 (RSC):
            서버 안에서 라이브러리를 실행해 결과(HTML)만 만들고, 라이브러리 JS는 보내지 않음

```

| 구분                            | CSR / 클라이언트 컴포넌트                         | Next.js 서버 컴포넌트 (RSC)                            |
| :------------------------------ | :------------------------------------------------ | :----------------------------------------------------- |
| **npm install 위치**            | 배포 서버 / 개발자 컴퓨터                         | 배포 서버 / 개발자 컴퓨터                              |
| **사용자 브라우저로 전송 여부** | ⭕ 라이브러리 JS 코드가 전송됨                    | ❌ 라이브러리 JS 코드가 안 넘어감                      |
| **브라우저의 부담**             | 브라우저가 JS를 받아와서 실행함<br>(용량↑, 속도↓) | 서버가 다 실행하고 결과(HTML)만 받음<br>(용량 0바이트) |

4. [Deep Dive] RSC의 4단계 동작 과정

4-1) RSC의 4단계 동작 과정

```
[1. 요청] 사용자의 페이지 접속
  └─► [2. 서버 실행] DB 직접 조회 및 컴포넌트 연산
        └─► [3. 직렬화] 연산 결과를 RSC Payload(JSON 형태의 경량 텍스트 지시서)로 압축
              └─► [4. 스트리밍] 브라우저로 지시서 전달 후 즉시 화면 완성
```

4-2) 하이브리드 모델과 'use client'

- 모든 요소가 서버에만 존재할 수는 없습니다. 클릭 이벤트, useState 등 사용자 상호작용이 필요한 부분만 클라이언트 컴포넌트로 분리합니다.
- 서버 컴포넌트 (주방): 무거운 DB 조회 및 뼈대 연산 담당 (기본값)
- 클라이언트 컴포넌트 (홀 직원): 사용자와 대화하고 주문 및 상호작용 담당 ('use client' 명시)

```javascript
"use client"; // 👈 주방(서버)에서 홀(브라우저)로 나가기 위한 출입증!

import { useState } from "react";

export default function LikeButton() {
  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>❤️ {likes}</button>;
}
```

4-3) 렌더링 방식 비교 (CSR vs SSR vs RSC)

| 구분               | CSR               | SSR                   | RSC (Next.js App Router)        |
| ------------------ | ----------------- | --------------------- | ------------------------------- |
| **렌더링 주체**    | 브라우저 (Client) | 서버 + 브라우저       | 서버 중심 (필요한 곳만 Client)  |
| **JS 번들 크기**   | 매우 큼           | 큼                    | 최소화 (Zero Bundle Size 지향)  |
| **SEO 지원**       | 불리함            | 우수함                | 매우 우수함                     |
| **DB 직접 접근**   | 불가능 (API 필요) | 가능                  | 가능 (컴포넌트 내 직접 가능)    |
| **초기 로딩 속도** | 느림 (하얀 화면)  | 빠름 (HTML 즉시 전송) | 가장 빠름 (HTML + 최소 JS 전송) |

4-4)'use client'에 대한 흔한 오해와 실제 동작

❌ 흔한 오해

- 'use client'를 쓰면 순수 React(CSR)처럼 서버는 아무것도 하지 않고, 브라우저가 자바스크립트(JS)를 받아 빈 화면에서 처음부터 끝까지 그린다는 오해.

⭕ 실제 동작

- 'use client'는 서버 렌더링 결과물 위에 클라이언트 전용 인터랙션을 붙이는 경계선(Boundary)을 의미합니다.
- 클라이언트 컴포넌트도 초기 로딩 시에는 서버에서 HTML 뼈대를 미리 작성하여 내려보냅니다.
- 클릭 이벤트나 상태(useState) 같은 인터랙션 기능만 뺀 채로 먼저 전달됩니다.

4-5) 하이드레이션(Hydration)과 경계선(Boundary)

- 비유: 마네킹과 영혼 (하이드레이션)

```
1. 서버의 역할 (1단계: HTML 생성)

서버는 버튼, 텍스트 등이 포함된 마네킹(HTML)을 완벽한 모양으로 만들어서 브라우저에 바로 전달합니다.
사용자는 하얀 화면 대신 완성된 화면을 즉시 확인합니다. (SEO 대응 가능)
다만 이 시점의 버튼은 클릭해도 동작하지 않는 마네킹 상태입니다.

2. 브라우저의 역할 (2단계: 하이드레이션)
브라우저로 onClick, useState 등의 인터랙션 코드가 담긴 JS 파일이 다운로드됩니다.
React가 이미 만들어진 HTML 마네킹 위에 JS 이벤트를 결합하여 움직이는 상태로 만듭니다. 이 과정을 하이드레이션(Hydration, 물 주기)이라 합니다.

3.  'use client'가 '경계선(Boundary)'인 이유
Next.js App Router는 기본적으로 모든 파일이 서버 컴포넌트(RSC)입니다. 특정 파일 상단에 'use client'를 선언하는 것은 다음과 같은 표식입니다.
"여기서부터 하위로 불러오는(import) 모든 컴포넌트와 코드는 브라우저용 JS 번들에 포함하고, 브라우저에서 하이드레이션을 진행해 줘!"
즉, 서버 전용 영역(RSC)과 클라이언트 JS 영역을 구분 짓는 경계선일 뿐, 서버 렌더링 자체를 끄는 옵션이 아닙니다.

```

| 구분                        | 'use client' 선언 전 (서버 컴포넌트) | 'use client' 선언 후 (클라이언트 컴포넌트) |
| --------------------------- | ------------------------------------ | ------------------------------------------ |
| **서버에서 HTML 생성 여부** | ⭕ 생성함                            | ⭕ 생성함 (초기 렌더링)                    |
| **브라우저로 JS 파일 전송** | ❌ 안 보냄 (0바이트)                 | ⭕ 보냄 (하이드레이션 전용 JS)             |
| **가능한 기능**             | DB 직접 조회, async/await            | useState, useEffect, onClick 등            |

4-6) Next.js는 기본적으로 SSR인가, CSR인가?

- Next.js는 기본적으로 '서버 중심(Server-First / 넓은 의미의 SSR)'이며, CSR이 아닙니다. 기본은 서버에서 다 처리하고, 필요한 부분만 클라이언트(CSR)에 맡기는 하이브리드 방식

- Next.js 기본 렌더링 구조

```
- 기본 상태 ('use client' 미선언 시) : RSC (React Server Components)

전통적인 SSR에서 한 단계 더 발전한 서버 전용 렌더링입니다.
서버에서 데이터베이스 조회와 연산을 마무리한 뒤 완성된 결과만 전송하며, 전송되는 JS 용량은 0바이트에 가깝습니다.

- 'use client' 선언 시 : 전통적인 SSR + CSR (하이드레이션)
1차 (SSR): 서버에서 HTML 뼈대를 먼저 그려 전달합니다.
2차 (CSR): 브라우저가 자바스크립트를 받아와 이벤트와 상태를 연결(Hydration)합니다.

```

4-7) SSR과 RSC의 핵심 차이점

- SSR: 페이지의 초기 렌더링 속도(첫 화면 표시)를 높이기 위해 서버에서 HTML 뼈대를 미리 그려주는 기술/기법입니다.

- RSC: 브라우저로 전송되는 JS 번들 크기를 줄이고 데이터 접근 구조를 단축하기 위해 도입된 컴포넌트 단위 아키텍처(구조)입니다.

- 핵심 차이 3가지

```
- 처리 단위 (페이지 vs 컴포넌트)

SSR: 페이지 단위(Page level)로 작동합니다. 요청된 전체 페이지의 HTML을 서버에서 한 번에 렌더링합니다.
RSC: 컴포넌트 단위(Component level)로 작동합니다. 한 페이지 안에서도 특정 컴포넌트는 서버 전용(RSC), 특정 컴포넌트는 클라이언트용('use client')으로 자유롭게 조합할 수 있습니다.

- 브라우저로 전달되는 JS 용량

SSR: 초기 화면은 빠르지만, 하이드레이션을 위해 해당 페이지의 모든 컴포넌트 JS 코드를 브라우저로 다운로드해야 합니다.
RSC: 서버 컴포넌트의 JS 코드는 브라우저로 절대 전달되지 않습니다 (Zero Bundle Size). 연산 결과(RSC Payload / HTML)만 전달됩니다.

- 클라이언트 상태(State) 유지 능력
SSR: 페이지를 SSR 방식으로 다시 가져오면(서버 재요청), 기존 React State(useState 값 등)가 초기화됩니다.
RSC: 서버 컴포넌트가 다시 실행되어 데이터를 새로 가져오더라도, 클라이언트 컴포넌트의 React State는 파괴되지 않고 유지됩니다.


```

4-8) RSC에서 클라이언트 State가 유지되는 원리

- 데이터를 다시 가져올 때(예: router.refresh() 실행 시) 전체 페이지를 새로고침(Full Page Reload)하지 않고, React의 비교(Reconciliation) 및 스트리밍 알고리즘을 사용하기 때문입니다.

```
- 1단계: 백그라운드 요청
브라우저는 페이지 전체를 다시 그리는 대신, 백그라운드로 서버에 데이터를 요청합니다.

- 2단계: RSC Payload(지시서) 수신
서버는 HTML 문서를 다시 보낸 것이 아니라, 가벼운 JSON 형태의 화면 구조 지시서(RSC Payload)를 전송합니다.
// RSC Payload 예시
"서버 컴포넌트 [ProductList] 영역의 최신 데이터는 A, B, C입니다."
"클라이언트 컴포넌트 [Counter] 영역은 그대로 유지하세요."

- 3단계: Virtual DOM 재조정 (Reconciliation)
브라우저의 React는 수신한 지시서와 현재 화면(Virtual DOM)을 비교합니다.
서버 컴포넌트 영역: 데이터가 바뀐 부분만 패치(Patch)합니다.
클라이언트 컴포넌트 영역: 컴포넌트의 위치와 Key가 동일하다면 인스턴스를 삭제하지 않고 유지합니다.
핵심: 클라이언트 컴포넌트 메모리가 유지되므로, 해당 컴포넌트가 가지고 있던 useState 상태 또한 손상되지 않고 유지됩니다.

```
