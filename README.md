# Next.js 앱 구조 설계: Route Groups & Private Folders

## 1. 왜 구조 분리가 필요할까?

실무에서는 마케팅 랜딩 페이지(화려한 상단 바, 가벼운 컨텐츠)와 관리자 대시보드(복잡한 좌측 사이드바, 데스크톱 앱 같은 레이아웃)가 하나의 프로젝트에 함께 공존합니다.

- **문제점:** 하나의 `layout.tsx` 안에서 조건문(`if/else`)으로 레이아웃을 처리하려고 하면 코드가 금세 지저분해집니다.
- **해결책:** Next.js의 **Route Groups**와 **Private Folders**를 활용해 URL 주소 오염 없이 레이아웃을 깔끔하게 격리합니다.

## 2. Route Groups: URL에서 사라지는 '투명 망토' `(folderName)`

폴더 이름을 소괄호로 감싸면 브라우저의 URL 경로 계산에서 완전히 제외됩니다.

- **구조 재설계 가이드:** 충돌 방지를 위해 기존 최상위 `src/app/layout.tsx`를 삭제하고, 그룹별 폴더를 생성합니다.

```text
src/app/
├── (marketing)/       # URL에 반영 안 됨 (예: / 접속)
│   ├── layout.tsx     # 마케팅 전용 루트 레이아웃 (html, body 포함)
│   └── page.tsx
│
└── (app)/             # URL에 반영 안 됨 (예: /dashboard 접속)
    ├── layout.tsx     # 앱 전용 루트 레이아웃 (html, body 포함)
    └── dashboard/
        └── page.tsx

```

- **핵심 특징:**
- **레이아웃 격리:** 각 그룹 폴더 안에 `layout.tsx`를 따로 두어 마케팅 페이지와 대시보드의 배경색, 폰트, 헤더/푸터 구조를 완전히 다르게 가져갈 수 있습니다.
- **주의사항:** 최상위 레이아웃을 삭제했으므로 각 그룹의 `layout.tsx` 상단에 `import "@/app/globals.css";`를 직접 작성해 주어야 테일윈드가 정상 작동합니다.
- **실무 팁:** `<html>`과 `<body>` 태그에 `suppressHydrationWarning`을 추가해 브라우저 확장 프로그램으로 인한 불필요한 하이드레이션 경고를 방지합니다.

## 3. Private Folders: 폴더를 감추는 '비밀 금고' `_folderName`

폴더 이름 앞에 언더바(`_`)를 붙이면 Next.js 라우터가 해당 폴더를 인식하지 못합니다.

- **역할:** `/src/app/_utils/date-formatter.ts`처럼 만들면, 브라우저 주소창에 `/_utils/...`로 직접 접근했을 때 무조건 **404 에러**가 발생합니다.
- **장점:** 관련 유틸리티나 컴포넌트를 페이지 바로 옆에 안전하게 두는 **Colocation(공동 배치)** 방식을 구현할 수 있습니다.

# 서버 컴포넌트(RSC)와 클라이언트 컴포넌트 (`"use client"`)

## 1. 리액트 개발자를 당황시키는 Next.js의 변화

전통적인 SPA(Single Page Application)와 달리, Next.js 15+ 앱 라우터는 모든 컴포넌트가 기본적으로 '서버 컴포넌트(Server Component)'로 동작합니다.

- **서버 컴포넌트 (주방에서 요리를 끝내고 나오는 접시):**
- 서버에서 HTML을 완벽하게 완성해서 브라우저로 보냅니다.
- **장점:** 자바스크립트 번들 크기가 줄어들어 초기 로딩 속도(FCP)가 압도적으로 빠르고, 검색 엔진 크롤러가 내용을 쉽게 읽어 **SEO에 극도로 유리**합니다.
- **치명적 한계:** 서버는 브라우저처럼 지속적인 메모리 공간(Context)이 없고 물리적 클릭 신호를 받을 수 없으므로, 기본 상태에서는 `useState`, `useEffect`나 `onClick` 같은 이벤트 핸들러를 사용할 수 없습니다. _(에러 발생)_

## 2. 구원투수: `"use client"` 지시어

파일 최상단(임포트문보다 위)에 문자열 형태로 `'use client';`를 선언하면, Next.js에게 "여기서부터는 브라우저에서 실행될 수 있게 자바스크립트를 함께 보내줘!"라고 명령하는 경계선(Boundary)이 만들어집니다.

- **하이드레이션(Hydration):** 서버에서 받아온 메마른 정적 HTML 뼈대 위에 자바스크립트가 결합되어 기능(이벤트 리스너 등)에 숨을 불어넣는 과정입니다.

## 3. 서버 vs 클라이언트 선택 가이드

| 구분          | 서버 컴포넌트 (Default)              | 클라이언트 컴포넌트 (`"use client"`)    |
| ------------- | ------------------------------------ | --------------------------------------- |
| **핵심 역할** | 데이터 렌더링, SEO 최적화, 보안 유지 | 사용자 인터랙션 처리, 브라우저 API 접근 |
| **사용 시기** | • DB 직접 조회 및 서버 API 호출<br>  |

<br>• 민감한 API 비밀키 처리<br>

<br>• 블로그 글, 상품 상세 설명 등 정적 텍스트 | • `onClick`, `onChange`, `onSubmit` 등 이벤트<br>

<br>• `useState`, `useEffect` 등 리액트 훅 상태 관리<br>

<br>• `window`, `localStorage` 등 브라우저 전용 Web API |

## 4. 실무 핵심 아키텍처: 나뭇잎 컴포넌트 패턴 (Leaf Component Pattern)

에러가 난다고 해서 페이지 전체(`page.tsx`) 상단에 무작정 `'use client'`를 붙이면 서버 컴포넌트의 강력한 장점을 모두 잃게 됩니다.

- **해결법:** 페이지 전체는 서버 컴포넌트로 유지하고, 상호작용이 필요한 아주 작은 조각(예: 좋아요 버튼, 토글 메뉴 등)만 따로 분리하여 트리의 끝단(나뭇잎)에 배치합니다.
- **효과:** 브라우저가 다운로드해야 할 자바스크립트 번들 크기가 획기적으로 줄어들어 전체 앱의 성능(TTI)이 극대화됩니다.

## 5. 관련 질문들

### 클라이언트 컴포넌트는 어디까지 서버 렌더링을 하는가?

```
'클라이언트 컴포넌트'라는 이름 때문에 서버에서는 아무 작업도 안 하고 브라우저가 모든 걸 다 처리한다고 오해하기 쉽지만, **Next.js는 클라이언트 컴포넌트라 할지라도 첫 번째 요청(Initial Page Load) 시 서버에서 먼저 HTML을 생성해서 보냅니다.**
구체적인 동작 과정은 다음과 같습니다.

1. **서버에서의 사전 렌더링 (Prerendering / SSR):**

- 사용자가 페이지에 접속하면, 서버는 클라이언트 컴포넌트의 초기 상태(Initial State)를 바탕으로 **HTML 뼈대를 먼저 완성**합니다. (이때 자바스크립트 실행 코드가 붙은 완전한 인터랙션이 가능한 상태는 아닙니다.)

2. **브라우저로 전달 및 정적 화면 표시:**

- 서버가 만든 HTML을 브라우저에 보내주기 때문에, 사용자는 자바스크립트 파일이 다 다운로드되기도 전에 **화면의 뼈대(텍스트, 레이아웃 등)를 아주 빠르게 볼 수 있습니다.**

3. **하이드레이션 (Hydration):**

- 그 후 브라우저가 자바스크립트 파일을 다운로드하고 실행하여, HTML에 이벤트 리스너(`onClick` 등)와 훅(`useState` 등)을 연결해 '살아 움직이는' 상태로 만듭니다.

즉, "HTML 구조(마크업)를 만들어내는 초기 렌더링은 서버에서 공통으로 수행"하지만, "사용자의 상호작용에 따른 동적 업데이트와 리액트 훅 실행은 브라우저(클라이언트)에서 담당"한다고 이해하시면 됩니다.


```

### SEO(검색 엔진 최적화)가 서버 컴포넌트와 같은 건가?

```

결론부터 말씀드리면 "다르지만, 둘 다 SEO에 유리하다"고 보는 것이 정확합니다. 개념과 작동 방식을 비교해 보면 이렇습니다.

- **서버 컴포넌트의 SEO:**
- 서버에서 데이터베이스나 API 조회까지 완전히 끝마친 **완제품 HTML**을 만들어 보냅니다. 검색 엔진 크롤러(로봇)가 페이지를 읽었을 때 자바스크립트를 실행할 필요조차 없이 완벽한 콘텐츠(본문, 상품 정보 등)가 곧바로 담겨 있어 **SEO에 극도로 유리**합니다.

- **클라이언트 컴포넌트의 SEO:**
- Next.js 환경에서는 클라이언트 컴포넌트도 **초기 HTML을 서버에서 렌더링해서 보내주기 때문에** 검색 엔진 크롤러가 기본적인 텍스트와 구조를 읽어갈 수 있습니다. 과거 순수 클라이언트 전용 리액트(SPA) 앱에 비해서는 SEO가 훨씬 잘 되는 편입니다.
- 다만, 클라이언트 컴포넌트 내부에서 `useEffect` 등으로 나중에 데이터를 불러오는 영역은 초기 HTML에 포함되지 않으므로, 크롤러의 성능에 따라 비동기 데이터 수집에 제약이 생길 수 있습니다.


```

## 6. 요약

- **서버 컴포넌트:** 데이터까지 완전히 포함된 최종본 HTML을 서버에서 완성해 주므로 **가장 완벽한 SEO**를 보장합니다.
- **클라이언트 컴포넌트:** 초기 HTML 뼈대는 서버에서 만들어 주어 기본 SEO는 방어하지만, 동적 상호작용과 자바스크립트 의존성이 크기 때문에 메인 콘텐츠는 서버 컴포넌트에 맡기고 인터랙션만 클라이언트 컴포넌트로 분리(나뭇잎 패턴)하는 것이 SEO와 성능 모두를 잡는 베스트 실무 전략입니다.
